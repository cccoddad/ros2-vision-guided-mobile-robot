## 真实协议的明确边界

`protocol/README.md` 中的 V1 帧头、版本、长度、序号和 CRC 仍是可测试的通用封装；其中 11 字节 `BASE_STATUS` 仅供 FakeTransport 单元测试。它不是 STM32 已冻结字段，不能直接写入固件或接入真实串口/CAN。

硬件到位后，必须先填写 [真实 BASE_STATUS 字段评审模板](../protocol/BASE_STATUS_REVIEW_TEMPLATE.md)，确认编码器、轮速、电池、驱动器故障、急停、时间基准、字节序、缩放、无效值和版本策略。STM32 始终是急停、通信超时、PWM 禁用和硬件故障的最终安全权威。

## 新对话的无硬件复现命令

以下整段命令仅在 VMware Ubuntu 终端执行；它不访问真实硬件，不修改系统配置。构建目录始终在 `$HOME/robot_ws_build`，而不是共享源码目录。

```bash
source /opt/ros/jazzy/setup.bash
cd /mnt/hgfs/robot_project

export ROS_LOCALHOST_ONLY=1
export ROS_DOMAIN_ID=42
BUILD_ROOT="$HOME/robot_ws_build"

PROTOCOL_BUILD="$BUILD_ROOT/protocol"
mkdir -p "$PROTOCOL_BUILD"
cc -std=c11 -Wall -Wextra -Werror -pedantic \
  -I protocol/include \
  protocol/src/robot_protocol.c \
  protocol/test/test_robot_protocol.c \
  -o "$PROTOCOL_BUILD/test_robot_protocol"
"$PROTOCOL_BUILD/test_robot_protocol"

colcon --log-base "$BUILD_ROOT/log" build \
  --build-base "$BUILD_ROOT/build" \
  --install-base "$BUILD_ROOT/install" \
  --packages-up-to base_driver parking_controller robot_simulation \
  --event-handlers console_direct+

source "$BUILD_ROOT/install/robot_interfaces/share/robot_interfaces/local_setup.bash"
colcon test \
  --build-base "$BUILD_ROOT/build" \
  --install-base "$BUILD_ROOT/install" \
  --packages-select base_driver parking_controller \
  --event-handlers console_direct+
colcon test-result --test-result-base "$BUILD_ROOT/build" --verbose

python3 scripts/run_sil_parking_regression.py
git diff --check
git status --short
```

- `source /opt/ros/jazzy/setup.bash`：使当前终端能找到 ROS 2 命令；不会修改 `.bashrc`。
- `ROS_LOCALHOST_ONLY=1` 与 `ROS_DOMAIN_ID=42`：把本次 ROS 2 通信限制在 VMware 内并统一测试域；Jazzy 的弃用警告已知，但该设置在本项目本机 SIL 中可用。
- `cc -std=c11`：独立编译纯 C 协议测试；`-Werror` 会把编译警告视为错误。
- `colcon ... build`：只把 ROS 2 构建产物写入 `$BUILD_ROOT`；`--packages-up-to` 同时构建所需依赖。
- `local_setup.bash`：补足隔离安装时 `robot_interfaces` 的运行时环境，避免回归脚本找不到 `/park_to_tag` 所需接口。
- `colcon test` 与 `test-result`：运行并汇总 C++ 单元测试；`run_sil_parking_regression.py`：顺序验证正常泊车和 Tag 丢失停止。
- `git diff --check` 与 `git status --short`：检查格式与未提交改动，不会修改源码。

如果 `ROS_LOCALHOST_ONLY` 警告出现，它是 Jazzy 对旧环境变量的弃用提示，不等同于测试失败；应以 Action、测试和回归脚本的最终 `PASS`/失败输出判断。若 `/park_to_tag` 在 5 秒内不可用，先重新加载上述 `robot_interfaces/local_setup.bash`，再检查构建结果，不要把该症状直接归因于泊车算法。

## 硬件到位后的顺序（未执行）

1. 收集电机驱动器、编码器、BMS、电池、急停和 UART/CAN 的数据表、接线与电气规格。
2. 填写并冻结 `BASE_STATUS` 评审模板；在未冻结前不得复用 SIL 11 字节字段。
3. 在 STM32 台架先验证独立急停、上位机命令超时、PWM 禁用和故障锁存；此时仍不做泊车运动测试。
4. 获得用户对真实硬件操作的明确授权后，再实现经评审的 C++ 真实 Transport，并从受控低速台架开始 HIL 测试。
5. 依照证据索引登记 HIL 协议、安全、里程计和视觉证据；通过前不得宣称实车能力完成。

## 风险与交接结论

- 本阶段的所有“通过”均为 C/C++ 单元测试或 Gazebo SIL 结果。
- `DriverHealth` 和 ROS 2 状态只能报告/诊断，不能替代 STM32 的急停、看门狗、PWM 或硬件故障决策。
- Python 仅用于 launch、Gazebo/SIL 回归和测试工具；`base_driver` 的生产路径保持 C++17、`ament_cmake`、`rclcpp` 方向。
- 开始硬件阶段前，优先阅读本文件、[第 7 步记录](07_阶段实施记录与下一步.md)、[协议评审模板](../protocol/BASE_STATUS_REVIEW_TEMPLATE.md)和[测试证据索引](../test_results/README.md)。
