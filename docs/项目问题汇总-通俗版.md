# 项目问题汇总 - 通俗版

## 先说结论

这个项目现在已经可以在 Ubuntu 虚拟机里演示一台“虚拟小车”：它能在 Gazebo 中接收速度命令、看见模拟的 AprilTag、自动停在 Tag 前面；如果 Tag 突然消失，它会停下来。

这里的“看见”是程序直接根据 Gazebo 的位置计算出来的模拟数据，不是连接真相机；“停车”也是虚拟小车停车，不是电机真的停转。下面记录的是开发时真实遇到的坑，以及我们怎么处理的。

## 1. 不需要重装 Ubuntu

**当时担心什么**：虚拟机里已经有很多软件和 RK3568 项目，怕为了 ROS 2 再装一个 Ubuntu，或者把原来的系统弄坏。

**最后怎么做**：直接复用了原来的 Ubuntu 24.04.3，只补装 ROS 2 Jazzy 和 Gazebo。没有重装系统，也没有删除旧项目。

**记住一句话**：ROS 2 是装在 Ubuntu 里的软件，不是一套必须单独重装的操作系统。

## 2. 软件安装很久，不等于一定死机

**看到的情况**：第一次装 ROS 2 和 Gazebo 时，终端下载了很多包，虚拟机也明显变慢。

**原因**：这是两个很大的软件，下载、解压和配置都会吃网络、CPU 和磁盘。虚拟机资源比本机少，所以看起来更慢。

**怎么处理**：先等；如果真的卡死就正常重启，再让 Ubuntu 修复未配置完的软件包后重试。已经下载好的部分通常会留在缓存里，不需要全部重下。

## 3. 有时不是终端退出，而是命令提前停了

**看到的情况**：复制一整段命令后，编译失败，后面本该启动的程序没有出现，好像“终端自己退出”。

**原因**：命令中用了 `&&`。它的意思是“前一条成功，才执行后一条”。编译出错后，后面的启动命令自然不执行，但终端仍然可以继续输入。

**怎么处理**：看第一条 `Error`，不要只看最后的“找不到包”。最后的错误很多时候只是前面构建失败带出来的结果。

## 4. `colcon` 的参数位置不能随便换

**看到的情况**：终端说不认识 `--log-base`，构建根本没开始。

**原因**：`colcon` 把参数分成“总参数”和“build 专用参数”。`--log-base` 必须在 `build` 前面，其他两个目录参数放在 `build` 后面。

**正确写法**：

```bash
colcon --log-base "$BUILD_ROOT/log" build \
  --build-base "$BUILD_ROOT/build" \
  --install-base "$BUILD_ROOT/install"
```

**记住一句话**：终端命令看起来像一句话，但参数位置本身也是语法。

## 5. 代码可以放共享目录，编译结果不要放那里

**看到的情况**：Windows 和 Ubuntu 的共享目录能看到源码，但 ROS 2 编译经常出奇怪问题。

**原因**：ROS 2 编译会产生很深的文件夹和很多链接；VMware 共享文件夹对这些 Linux 文件操作支持不如 Ubuntu 本机磁盘稳定。

**怎么处理**：源码仍放在 `/mnt/hgfs/robot_project`，这样 Windows 和 Ubuntu 都能看到；编译结果放到 Ubuntu 本机的 `$HOME/robot_ws_build`。

**打个比方**：共享目录像公共展示柜，适合放图纸；本机目录像加工车间，适合编译产生很多零件。

## 6. 编译成功后，也要让新终端“认识”这个包

**看到的情况**：屏幕已经显示 `Finished <<< robot_simulation`，但下一句又说找不到 `robot_simulation`。

**原因**：编译只是把包安装好了；每一个新终端还要加载它的位置。虚拟机里有旧工作区路径时，总环境脚本有时不会自动带上新包。

**怎么处理**：先加载 ROS 2，再加载工作区环境；必要时单独加载这个包的 `local_setup.bash`，最后用下面命令确认：

```bash
ros2 pkg prefix robot_simulation
```

它输出安装目录，才说明这个终端真的能找到该包。

## 7. 看见 Gazebo 窗口，不代表所有程序都启动了

**看到的情况**：Gazebo 画面开着，但自动泊车一直显示“等不到 Tag”，随后失败。

**原因**：自动泊车除了 Gazebo 画面，还需要“翻译员”和“模拟 Tag 发布器”：前者把 Gazebo 的位置翻成 ROS 2 的 `/odom`，后者再根据 `/odom` 计算 `/sim/tag_pose`。只开画面时，这两项可能没有启动。

**怎么处理**：必须用项目的启动命令启动完整链路：

```bash
ros2 launch robot_simulation gazebo.launch.py
```

看到 `Publishing synthetic TagPose on /sim/tag_pose` 才说明模拟 Tag 数据正在发出。

## 8. 虚拟机的网络让 ROS 2 节点互相“看不见”

**看到的情况**：有时会报“发送组播消息：网络不可达”，一个终端启动的节点，在另一个终端中找不到。

**原因**：ROS 2 默认会用一种叫 DDS 的机制自动寻找同伴，其中会使用组播网络；这台 VMware 的网络环境不支持这种组播。

**怎么处理**：每个参与测试的终端都加上：

```bash
export ROS_LOCALHOST_ONLY=1
export ROS_DOMAIN_ID=42
```

前一句让通信只在当前虚拟机内部寻找，后一句让所有终端进入同一个“房间”。这样不改系统网络设置，关闭终端后也自动失效。

## 9. 远远看着小车，难以判断它到底有没有动

**看到的情况**：Gazebo 里小车很小，肉眼看不出它是动了一点还是根本没动。

**怎么处理**：不靠眼睛判断，运行 `verify_gazebo_motion.py`。它会读小车起点和终点的位置，算出移动距离和转了多少角度。这次测到了移动 `0.579 m`、转动 `1.421 rad`。

**记住一句话**：画面适合展示，数字才适合验收。

## 10. 测试脚本也会因为 ROS 2 版本变化出错

**看到的情况**：测试“Tag 消失后是否停车”时，Python 报 `AttributeError`，说某个方法不存在。

**原因**：这个脚本的旧写法和 ROS 2 Jazzy 的参数客户端接口名称不一致。

**怎么处理**：改成 Jazzy 使用的 `wait_for_services()` 和 `services_are_ready()`，再重新跑测试。

**结果**：Tag 消失后，任务失败码是 `1`，小车线速度和转速都是 `0.0000`，说明它没有继续往前走。

## 11. Python 原型不能直接当成最终实机控制程序

**看到的情况**：最早的停车控制器是 Python 写的，虽然仿真能跑，但和项目“实机 ROS 2 节点用 C++”的规则不一致。

**原因**：Python 很适合快速写仿真、测试和工具；但真实小车的停车状态机、速度限制和故障处理属于正式运行链路，需要 C++ 版本。

**怎么处理**：把停车控制器迁移为 C++，但保留了原来的话题名、Action 名、参数名和失败代码。这样测试脚本不用改，就能继续验证新的 C++ 程序。

## 12. “任务失败”还不够，要确认车真的停了

**看到的情况**：程序说 Tag 丢失、任务失败，但这不一定能证明小车没有沿用上一条速度命令继续走。

**怎么处理**：测试不仅检查 Action 的失败码，还检查 Gazebo `/odom` 中的线速度和转速。

**结果**：两项都是 `0.0000`。这才说明完整链路是“Tag 消失 -> 控制器发停止命令 -> 虚拟小车速度归零”。

## 13. 测试说“找不到停车服务”，不一定是 C++ 程序坏了

**看到的情况**：第一次跑整套 SIL 泊车回归时，脚本等了 5 秒也找不到 `/park_to_tag`，因此直接失败。

**原因**：编译出来的接口包没有被这个终端完整加载。ROS 2 中“文件已经编译好”和“当前终端知道去哪里找它”是两件事。

**怎么处理**：在加载 ROS 2 后，再加载 `robot_interfaces` 的 `local_setup.bash`，然后重新跑回归。这样正常停车和 Tag 消失后停止两项都通过了。

**记住一句话**：遇到“服务不存在”，先检查运行环境有没有加载全，不要马上怀疑业务代码。

## 14. 假状态包不能冒充真实 STM32 协议

**看到的情况**：为了测试底盘驱动，程序需要一份 `BASE_STATUS` 状态包；但真实编码器、电池、驱动器和通信参数都还没有。

**原因**：软件测试可以临时约定一组字节来模拟轮速、电压、故障和急停，但这些字节的含义不能替硬件工程师作决定。

**怎么处理**：假传输层只在内存里喂入 11 字节测试数据，不碰串口。另建了一张真实协议评审表，等硬件到位后再填写每个字段放在哪、单位是什么、哪些 bit 代表故障。

**记住一句话**：测试用的道具可以先有，真正的零件规格不能靠猜。

## 15. “有问题/没问题”两个状态不够用

**看到的情况**：坏 CRC、序号乱了、很久没收到消息、急停被按下，都会出问题，但严重程度不同。

**怎么处理**：用 C++ 做了一个状态模型，把“还没配置好、可以工作、普通通信警告、通信超时错误、急停错误”区分开，并写了测试验证优先级。

**特别要注意**：这个模型只是 ROS 2 上位机的健康记录，不能解除 STM32 的急停锁存，也不能重新打开 PWM。

## 16. ROS 2 的速度单位和 STM32 的速度单位不一样

**看到的情况**：`/cmd_vel` 用的是 m/s、rad/s 小数；协议帧用的是 mm/s、mrad/s 的整数。还要处理过快、无穷大和 NaN 这样的非法输入。

**怎么处理**：在 C++ 中先换算单位、按配置限速、拒绝非法数字，再编码成协议帧。所有检查都在内存测试中完成，没有给真电机发送命令。

**打个比方**：像把“公里”换成“米”之前，先检查数字有没有写错、有没有超过限速。

## 17. 测试通过的截图和日志，不能等到硬件来了才整理

**看到的情况**：协议测试、C++ 测试和 Gazebo 测试都各自有“PASS”，但没有一张总表说明它们只证明了软件，不证明实体车。

**怎么处理**：增加测试证据索引：已通过的项目都标为 SIL；未来真实协议、安全、编码器和相机测试先占好 HIL 位置，并要求写清命令、输入、实际结果和审核人。

**记住一句话**：软件通过和实体车通过，要放在两张不同的成绩单上。

## 18. PowerShell 会把 Git 的一段写法当成自己的命令

**看到的情况**：想查询 Git 正在跟踪哪个远程分支时，PowerShell 报语法错，推送也没有开始。

**原因**：Git 用 `@{u}` 表示“上游分支”，但 PowerShell 也把 `@{...}` 当成自己的语法。

**怎么处理**：给 Git 的这段内容加单引号：`'@{u}'`，再单独执行推送。最终正常推送，没有强制覆盖远程仓库。

## 现在已经做到什么

- Ubuntu 开发环境已能使用；
- 有模拟底盘、RViz 模型和 Gazebo 物理场景；
- 可以运行模拟 AprilTag 自动泊车；
- Tag 消失后可以停止；
- 停车控制器已经是 C++；
- 协议已有 C 语言的帧、CRC 与模糊测试；
- C++ 底盘驱动已有假传输、状态映射、故障优先级、命令限幅和配置校验；
- 正常泊车与 Tag 丢失停止的 SIL 回归已经通过；
- 真实 `BASE_STATUS` 协议字段与测试证据索引已建立，但仍待硬件确认。

## 还没有做到什么

- 没有真实摄像头和真实 AprilTag 识别；
- 没有串口/CAN、STM32、电机、编码器、PID 或 PWM；
- 没有实车里程计、真实急停、供电和碰撞安全验证；
- Gazebo 中跑通不代表拿到实体车就一定能跑通。

## 下一步简单说

硬件到位前的主要软件工作已经完成。现在不能直接把假数据接到 STM32 或让车运动；要先拿到电机、编码器、驱动器、电池/BMS 和 UART/CAN 的真实规格，填写并冻结 `BASE_STATUS` 评审表，再先做 STM32 自己的急停、断开上位机后超时、PWM 关闭和故障锁存台架验证。

完整交接命令、已完成项目和硬件阶段的前置条件见 [第 8 步：无硬件软件闭环与协议评审准备](08_无硬件软件闭环与协议评审准备.md)。
