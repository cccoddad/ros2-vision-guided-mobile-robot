# 项目问题汇总 - 面试版

## 项目背景

项目是 ROS 2 Jazzy + Gazebo Harmonic 的视觉引导移动机器人软件工程。开发阶段为软件在环（SIL）：没有连接电机、STM32、编码器或相机，目标是先验证 ROS 2 接口、Gazebo 闭环、停车状态机与故障停止语义。以下问题均来自实际开发和验证过程。

## 问题 1：已有 Ubuntu 环境能否复用

**现象**：已有 VMware Ubuntu 内含其他工程和工具，担心安装 ROS 2 会要求重装系统或影响既有 RK3568 工程。

**定位与决策**：ROS 2 Jazzy 与 Ubuntu 24.04 匹配，现有系统为 Ubuntu 24.04.3 x86_64；因此选择在原虚拟机增量安装与验证，不创建第二套系统，也不执行全量系统升级。

**处理**：只安装 ROS 2、Gazebo 和开发工具；不执行 `apt upgrade`，不改 `.bashrc`，每个终端按需 `source /opt/ros/jazzy/setup.bash`。

**工程价值**：控制了环境变更范围，避免“为了一个项目重置开发机”的高风险操作；说明了依赖版本兼容性和可复用环境的判断能力。

## 问题 2：大规模依赖安装缓慢、虚拟机短暂无响应

**现象**：首次安装 ROS 2 Desktop 与 Gazebo 时下载包很多，虚拟机界面看似卡住；用户担心中断后必须从头下载。

**定位**：`apt` 下载和解包会占用磁盘、CPU 与网络，尤其在虚拟机分配资源有限时更明显。已完整下载的 `.deb` 通常会被保留在本机缓存，重新执行安装命令会复用缓存并继续处理未完成包。

**处理**：等待当前包完成；若确实无响应则正常重启虚拟机，再执行 `sudo dpkg --configure -a`、`sudo apt -f install` 后重试原安装命令。没有删除软件包缓存或重置系统。

**工程价值**：区分“长时间安装”与“安装状态损坏”，采用可恢复的包管理修复流程。

## 问题 3：`colcon` 参数位置错误导致构建未开始

**现象**：终端提示 `colcon: error: unrecognized arguments: --log-base ...`，随后因为没有生成安装目录而出现“找不到包”或 `setup.bash` 的连带错误。

**定位**：`--log-base` 属于 `colcon` 全局参数，必须写在 `build` 子命令之前；`--build-base`、`--install-base` 才属于 `build` 子命令。

**处理**：改为 `colcon --log-base "$BUILD_ROOT/log" build --build-base ... --install-base ...`，并将正确格式固化到文档。

**工程价值**：从第一条错误定位根因，而不是处理后续派生错误；同时把命令行约束转化为可复用文档。

## 问题 4：VMware 共享目录不适合作为 ROS 2 构建目录

**现象**：源码在 `/mnt/hgfs/robot_project` 可读取，但 ROS 2 构建会因共享文件系统的深层路径、符号链接或元数据限制失败，导致包未安装。

**定位**：`rosidl` 消息生成与 CMake 安装会创建大量嵌套文件和链接；VMware HGFS 对这些构建行为的兼容性弱于 Linux 本地 ext4 文件系统。

**处理**：保留源码在共享目录，统一把 `build`、`install`、`log` 放在 Ubuntu 本机 `$HOME/robot_ws_build`。

**工程价值**：将“源码协作位置”和“构建产物位置”解耦，解决跨系统文件系统边界问题，同时不改变用户的 Windows 工作流。

## 问题 5：Python ROS 2 包未声明构建类型

**现象**：`base_driver_mock` 构建失败或没有生成可发现的包环境。

**定位**：包使用 Python 安装规则，但 `package.xml` 未明确声明 ROS 2 的 `ament_python` 构建类型，`colcon` 无法按预期处理。

**处理**：补充构建类型声明并重新构建，确认模拟底盘能够启动和发布话题。

**工程价值**：理解 ROS 2 包的元数据与实际构建系统必须一致；避免只根据源文件语言猜测构建方式。

## 问题 6：新包构建成功但 `ros2 launch` 仍找不到包

**现象**：`robot_simulation` 显示 `Finished`，但 `ros2 launch robot_simulation ...` 返回 `Package 'robot_simulation' not found`。

**定位**：虚拟机终端残留旧的 ROS 工作区路径，工作区总 `setup.bash` 没有把新安装包加入当前进程的搜索路径。

**处理**：在加载总工作区环境后，额外加载目标包的 `local_setup.bash`，并用 `ros2 pkg prefix robot_simulation` 验证包前缀后再启动。

**工程价值**：将“构建成功”和“运行时环境已加载”视为两个独立条件；用包前缀命令进行最小验证，而不是盲目重复编译。

## 问题 7：Gazebo 画面不易判断机器人是否真的移动

**现象**：远景中机器人尺寸很小，用户肉眼难以确认速度命令是否生效。

**定位**：可视化画面只能提供直观印象，不能作为运动链路的可靠验收证据。

**处理**：编写 `verify_gazebo_motion.py`，记录 `/odom` 起终点和航向，向 `/cmd_vel` 发送受限时命令，并以位移和转角阈值判定。例如一次验证得到 `0.579 m` 位移与 `1.421 rad` 转角变化。

**工程价值**：把主观观察改为可重复的度量测试，建立了 `/cmd_vel -> Gazebo -> /odom` 的端到端证据。

## 问题 8：Gazebo 启动但泊车控制器收不到模拟 Tag

**现象**：泊车 Action 在约 0.5 秒后返回 `failure_code=1`；`/sim/tag_pose` 的发布者数量为 0。

**定位**：只打开 Gazebo 图形界面不等于启动完整 ROS 仿真链路。模拟 Tag 发布器依赖 Gazebo 到 ROS 的 `/odom` 桥接；未通过 `robot_simulation` 启动文件启动时，该节点不存在。

**处理**：编译并通过 `ros2 launch robot_simulation gazebo.launch.py` 启动 Gazebo、`ros_gz_bridge` 与 `sim_tag_pose_publisher`。日志确认 `/cmd_vel`、`/odom` 桥接和 `/sim/tag_pose` 发布器均已创建。

**工程价值**：按数据依赖链定位问题：Action 等待 Tag，Tag 依赖 `/odom`，`/odom` 依赖桥接；而不是仅凭 GUI 是否出现判断系统是否启动。

## 问题 9：VMware 中 ROS 2 DDS 组播不可达，节点发现不稳定

**现象**：出现 `Exception sending a multicast message: 网络不可达`，或不同终端看不到 `/base_status`、`/sim/tag_pose` 的发布者。

**定位**：ROS 2 默认 DDS 使用网络发现；当前虚拟机网络接口无法正确发送组播，导致不同进程发现失败。

**处理**：在所有参与同一测试的终端统一设置 `ROS_LOCALHOST_ONLY=1` 与 `ROS_DOMAIN_ID=42`，限制通信到本机并固定同一域。Jazzy 会产生弃用警告，但该设置在本机验证中仍被支持。

**工程价值**：理解 ROS 2 节点通信不仅依赖代码，还依赖 DDS 发现域和网络环境；通过最小作用域的进程环境变量解决，而非修改系统网络配置。

## 问题 10：Jazzy 的 `AsyncParameterClient` API 与旧写法不兼容

**现象**：Tag 丢失测试脚本抛出 `AttributeError`，提示不存在 `wait_for_service` 和 `service_is_ready`。

**定位**：在当前 ROS 2 Jazzy 中，异步参数客户端使用复数 API：`wait_for_services()` 和 `services_are_ready()`；测试脚本仍使用旧名称。

**处理**：按 Jazzy API 改写测试脚本，并重新运行 Tag 丢失场景。结果为 `failure_code=1`、线速度和角速度均为零，测试通过。

**工程价值**：将框架升级差异定位在明确的运行时异常上，并用回归测试确认修复保持故障安全语义。

## 问题 11：Python 原型与 C++-first 项目边界冲突

**现象**：初版 `parking_controller` 使用 Python，和项目规定的实机 ROS 2 节点应为 C++/`rclcpp` 不一致。

**定位**：Python 适合仿真、launch 与测试工具，但实际停车状态机与速度控制属于生产运动链路，必须迁移为 C++，同时不能破坏既有 Action、话题、参数和失败代码。

**处理**：使用 C++17、`ament_cmake`、`rclcpp_action` 重写控制器；保留 Python 源文件作为迁移参考但不安装为运行节点。新增控制数学 GTest，并在 Gazebo 正常泊车与 Tag 丢失场景中验证接口兼容。

**工程价值**：完成了不破坏外部契约的渐进式技术迁移；区分了原型代码、仿真工具与生产运行链路。

## 问题 12：如何证明“故障时真的停车”

**现象**：控制器在 Tag 丢失时报告失败，不足以证明底盘没有继续执行旧速度命令。

**定位**：任务状态和执行器状态是两层不同的证据，必须同时验证 Action 结果和底盘里程计速度。

**处理**：`verify_tag_loss_stop.py` 在任务开始后关闭模拟 Tag，等待控制器超时，检查 `failure_code=1`，并读取 Gazebo `/odom` 的线速度、角速度。实际结果均为 `0.0000`。

**工程价值**：形成“故障输入 -> 控制器决策 -> 零速度输出 -> 运动状态归零”的闭环测试，而不是只验证日志文字。

## 问题 13：SIL 回归脚本找不到 `/park_to_tag` Action 服务

**现象**：首次运行 `run_sil_parking_regression.py` 时，脚本在 5 秒内等不到 `/park_to_tag`，因此以状态码 `2` 退出。

**定位**：问题不在 C++ Action 本身，而在运行时环境覆盖不完整：只加载工作区总 `setup.bash` 时，当前终端没有发现 `robot_interfaces` 安装路径，导致启动链路无法正确装载所需接口。

**处理**：在已加载 ROS 2 环境后，显式加载 `$BUILD_ROOT/install/robot_interfaces/share/robot_interfaces/local_setup.bash`，再运行回归脚本。正常泊车与 Tag 丢失停止两个场景均通过。

**工程价值**：将“Action 服务不存在”与“构建失败”区分开来，按 ROS 2 运行时 overlay 逐层验证；对隔离安装空间，包能被当前进程发现是独立验收条件。

## 问题 14：没有硬件规格时不能把 SIL `BASE_STATUS` 负载冻结为真实协议

**现象**：`base_driver` 需要状态帧来测试解码、CRC、序号、超时和急停，但编码器位宽、电池量程、驱动器故障位、UART/CAN 参数均尚未确认。

**定位与决策**：测试需要可重复的字节布局，但测试布局不能倒推真实硬件契约。若直接把 11 字节 SIL 负载写进固件或公开文档，会使 ROS 2、STM32 和硬件的字段含义发生错误耦合。

**处理**：保持 V1 帧封装和 C 编解码器通用；仅在 FakeTransport 测试中使用 11 字节状态负载。新增 `protocol/BASE_STATUS_REVIEW_TEMPLATE.md`，要求在硬件到位后由 ROS、固件和安全人员确认偏移、缩放、故障位、无效值和冻结结论。

**工程价值**：把“通信帧的通用正确性”和“硬件业务字段的真实性”分层，避免仿真数据在后续硬件阶段演变成错误协议。

## 问题 15：传输异常不能只用一个布尔值表示

**现象**：接收状态帧时，CRC 错误、乱序、通信超时和急停的处理优先级不同；仅以“连接正常/不正常”无法表达能否激活、何时进入错误和何时允许恢复。

**定位**：错误分类、状态机和诊断输出应独立于真实串口，才能在硬件到位前用确定性测试覆盖边界。急停还必须高于 ROS 2 诊断和泊车状态。

**处理**：增加 C++ `DriverHealth` 状态模型与 GTest，覆盖未配置、激活前健康帧、协议警告、超时错误、急停优先级和健康恢复。它只建模上位机诊断状态，不解除 STM32 的硬件锁存。

**工程价值**：把故障优先级转化为可测试的状态转换规则，明确“ROS 2 只能报告和请求，STM32 才是 PWM 与急停最终权威”。

## 问题 16：速度命令需要协议单位、限幅和非法值的边界测试

**现象**：`/cmd_vel` 使用 m/s、rad/s 浮点数，而 V1 `SET_TWIST` 帧使用 `int16` 的 mm/s、mrad/s；无穷大或 NaN 以及超限输入会导致不安全或不可预测的编码结果。

**定位**：单位换算和限幅是 ROS 2 接口到 MCU 协议的边界，不能留给未来串口实现临时处理。

**处理**：实现 C++ `CommandFrameEncoder`，在纯内存中完成单位换算、配置限幅、序号递增和 C 帧编码；GTest 覆盖正常换算、限幅、非有限输入和非法配置。该组件没有接入真实串口或电机。

**工程价值**：提前锁定数值边界，降低真实链路接入时把异常 ROS 命令传递给下位机的风险。

## 问题 17：SIL 结果缺少统一的硬件验收追溯入口

**现象**：协议单测、C++ GTest 和 Gazebo 泊车回归分别有通过输出，但没有统一位置表明其测试类型、硬件结论和未来需要补齐的台架证据。

**定位**：测试通过不等于实车通过；没有证据索引时，容易把终端片段、SIL 结果和 HIL 结论混为一谈。

**处理**：新增 `test_results/README.md`，登记已执行的 SIL 编号与结果，并预建 HIL 协议、安全、里程计和视觉测试条目；索引禁止提交原始 rosbag、视频、密钥和个人数据。

**工程价值**：建立从提交、命令、产物到审核记录的追溯框架，使后续实机阶段能够补齐证据而不是重写历史结论。

## 问题 18：PowerShell 与 Git 上游分支语法冲突

**现象**：在 PowerShell 中执行包含 `@{u}` 的 Git 上游查询时，终端报“缺少哈希表键值运算符”，推送命令因整段脚本解析失败而没有执行。

**定位**：`@{...}` 同时是 PowerShell 哈希表语法和 Git 上游引用语法；未加引号时由 PowerShell 先解析。

**处理**：把 Git 引用写为单引号形式：`git rev-parse --abbrev-ref --symbolic-full-name '@{u}'`，然后单独重新执行 `git push origin main`。推送成功，未使用强推。

**工程价值**：区分 shell 解析错误与 Git 远程错误；先确认命令是否实际执行，再决定是否需要处理认证、冲突或远程历史问题。

## 当前风险与边界

- Gazebo 模型、模拟 Tag 位姿和参数均为软件在环数据，不能代表真实轮胎、打滑、相机、光照或延迟。
- `base_driver` 当前是 C++ 接口骨架，硬件传输被明确禁用；没有实机 `/odom` 或 TF。
- STM32 急停、通信超时、PWM 禁用、编码器与 PID 尚未实施或实测。
- 无硬件阶段的 C++ fake transport、协议状态映射、命令边界、诊断模型、协议模糊测试和 SIL 回归已完成；下一步须等待硬件规格确认并冻结真实字段，不能把 SIL 负载接入 STM32。
